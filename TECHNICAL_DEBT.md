# Technical Debt Register

This register covers verified, still-open risks in `9router-go` v1.9.1. It supersedes the former declarations that no critical, high, or medium debt existed. “Resolved” work from the changelog is not listed here unless it explains a remaining limitation.

Severity reflects operational impact if the condition occurs, not likelihood:

- **High** — can break startup/data integrity, expose sensitive data, or replace an executable from unverified input.
- **Medium** — can lose data, weaken verification, hang OAuth operations, or make performance/feature claims unreliable.
- **Low** — bounded maintenance or diagnostics gap with limited direct impact.

## Open risks

| ID | Severity | Risk and source evidence | Mitigation / next action (owner-style) |
|----|----------|-------------------------|----------------------------------------------|
| DB-01 | High | **Go has no production core-schema bootstrap or migration.** `internal/app/database.go` opens the configured file and creates only `upstream_leases`; `internal/db/client.go` contains PRAGMAs, not core DDL. `internal/dbtest/dbtest.go` is test-only. A blank DB can start but fail later when settings/API/auth queries encounter missing tables. | **Database/runtime owner:** add a versioned Go-owned schema manifest and startup compatibility check with an explicit migration strategy, or require and verify a compatible upstream-initialized DB before serving traffic. Add fresh-DB and old-schema tests. |
| DB-02 | High | **Credentials are plaintext and database dumps are sensitive.** Provider API keys, OAuth access/refresh tokens/client secrets, client API keys, and possibly proxy credentials are stored in `providerConnections.data`, `apiKeys.key`, and other JSON. `internal/db/client.go` only applies filesystem modes. Dashboard export includes these configuration rows. | **Security/data owner:** define the threat model and approved at-rest encryption/key-management design (or explicitly accept local-owner-only plaintext); audit every export/backup path, redaction boundary, retention policy, and restore process. Add tests that no secret escapes ordinary list/settings responses. |
| OPS-01 | High | **Updater integrity is optional and release fallback supplies no hash.** `internal/updater/updater.go` verifies SHA-256 only when `expectedSHA256` is non-empty. `version.json` currently has no checksum, and GitHub Releases fallback has no signed checksum/attestation. The updater then replaces the running binary. | **Release/security owner:** publish per-platform SHA-256 in a signed manifest or use signature verification bound to a pinned key; fail closed when verification is absent; verify the extracted executable against the manifest; test rollback and failed-verification paths. |
| VER-01 | Medium | **Concurrency fixes are not continuously race-verified.** CI runs `go test ./... -v` (`.github/workflows/ci.yml`) but not `go test -race ./...`; Makefile test targets are also non-race. Existing locks address several known issues, but statements such as “race-clean” are not maintained by CI. | **Go maintainers:** add at least Linux `go test -race ./...` (and a supported macOS runner if practical), keep race tests for shared caches, stream state, MITM, and HTTP paths, and make a new race report actionable rather than documenting it as resolved. |
| DATA-01 | Medium | **Diagnostics persist request/response content by default.** `internal/handlers/chat/usage.go` writes the last 20 truncated messages (500 chars each) and up to 10,000 response characters into `requestDetails.data`; `internal/db/usage.go` exposes the rows to the dashboard. There is no current Go retention/pruning implementation, and sensitive prompts/outputs remain in the DB. | **Product/privacy owner:** make diagnostics sampling and retention explicit, redact credentials/secret-like content, bound storage/age, and add authenticated delete/purge controls; document that the existing log is not a safe place for secrets. |
| OAuth-01 | Medium | **Some device/OAuth helpers discard request context.** `internal/handlers/oauth/device.go` uses `http.NewRequest` throughout polling, user-info, profile, and token helpers. Client cancellation, shutdown, and deadlines do not consistently cancel those outbound operations. | **OAuth maintainer:** thread `context.Context` through device start/poll and helper APIs, use `NewRequestWithContext`, and add cancellation/deadline tests for every provider family. |
| COMP-01 | Medium | **OAuth scope preservation is not uniformly verified.** Current OAuth write/refresh paths reconstruct dynamic JSON, while `internal/auth/token.go` has a fixed `TokenInfo.Scope` field and multiple provider-specific refresh implementations. A narrow comparison found paths that update the token response but do not uniformly prove that the original `scope` is retained across refresh/relogin. | **OAuth maintainer:** define whether scope is provider-specific, preserve an existing scope when a refresh response omits it, and test API-key/OAuth/device providers independently. Do not claim scope parity until this contract is encoded. |
| DB-03 | Medium | **Multi-process writes can lose data or state.** `internal/handlers/chat/usage.go` protects daily JSON merge with a process-local mutex; `internal/db/usage.go` replaces the full `usageDaily` row. `internal/db/dashboard.go` performs read/merge/write for settings without CAS, and several caches are process-local. WAL + a 5-second busy timeout do not make these operations cross-process atomic. | **Database owner:** either document/enforce a single active Go writer, or move aggregates/settings to transactionally mergeable rows/SQL-side updates. Add a two-process contention test and do not generalize `upstream_leases` beyond its registered scopes. |
| DB-04 | Medium | **Go writes optional columns absent from upstream v0.5.85.** `internal/db/usage.go:UpdateConnectionLastUsed` updates `lastUsedAt` and `consecutiveUseCount`; upstream `src/lib/db/schema.js` does not define them. Go does not add them, so metadata writes can fail on an otherwise compatible upstream-created DB. | **Schema owner:** reconcile ownership of these fields, migrate them explicitly, or derive them from supported upstream state. Add a fixture loaded from the actual upstream v0.5.85 schema and exercise a successful request. |
| BENCH-01 | Medium | **Published benchmark claims no longer validate the current proxy.** `benchmark/RESULTS.md` is dated 2026-07-18. Its native `benchmark/runner.go` says it starts 9router but actually serves a simple reverse-proxy wrapper, does not authenticate against SQLite, and does not exercise the real router. The old Next.js reproduction also depends on paths/build context not guaranteed by the current repository. | **Performance owner:** replace the wrapper with the compiled current server, use a versioned reproducible harness, record commit/toolchain/config, compare equivalent request paths, and avoid turning historical numbers into current guarantees. |
| DOC-01 | Medium | **Release and architecture documentation drifts from source.** The current release declares upstream v0.5.85, while `CHANGELOG.md` separately records selected v0.5.86 ports and one deferral. Older docs still describe a Next.js dashboard or blanket 100% parity, and the benchmark cites obsolete test counts/paths. | **Release/docs owner:** maintain one generated source of truth for Go version, declared upstream baseline, selected ports, accepted limitations, and benchmark provenance; add a doc drift check for version strings and “100% parity” claims. |
| CI-01 | Medium | **CI coverage does not prove the operational contract.** `.github/workflows/ci.yml` builds the SPA, vets, tests, and builds one binary, but does not race-test, boot a fresh DB, import an upstream v0.5.85 schema, exercise backup/restore permissions, run the real benchmark harness, or test updater verification failure. | **CI owner:** add a disposable integration job for upstream-schema boot, known migration failure, permission mode, configuration export/restore, and updater verification; keep live-provider tests opt-in. |

## Accepted limitations

These are operational or compatibility constraints, not claims that the risk has been eliminated:

1. **One active Go writer is the supported model.** SQLite may still be opened/read by a separate upstream process for controlled migration or inspection, but coordinated HA writers are not a supported topology. This is distinct from DB-03, which tracks accidental lost updates in shared-write deployments.
2. **Local-owner filesystem protection is the credential baseline.** `0700` on the immediate DB directory and `0600` on the main DB reduce access, but do not provide encryption, ACL management, or backup protection.
3. **OIDC/SAML configuration is partial.** The current server exposes OIDC/SAML tests and SAML metadata, but the Svelte UI advertises start routes that the Go router does not mount. Until implemented end to end, password login is the supported SSO-free path.
4. **The dashboard JSON export is configuration-only.** It intentionally omits usage history, daily aggregates, request details, leases, and upstream metadata; a physical SQLite backup is required for full recovery.
5. **Historical benchmark numbers are retained as historical context only.** They are not acceptance criteria or current release measurements.
6. **Provider behavior is conditional.** A route or catalog entry does not guarantee identical credentials, quotas, cloaking, or upstream response behavior across releases.

## Recently resolved, but not proof of zero debt

The changelog records fixes for stream state isolation, request-body bounds, response-body closure, graceful shutdown, OAuth error-body truncation, DB file permissions, registry synchronization, and MITM lifecycle races. Those are useful mitigations, but they do not replace CI race coverage, schema versioning, updater verification, retention policy, or two-process tests described above.
